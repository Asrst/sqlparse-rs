This is exactly the right call. Here's the full picture of what you're dealing with, the ecosystem of similar projects, and how to build it.

---

### What sqlparse actually does (from reading the source)

The library has 4 main operations:

| Function | What it does | Measured latency |
|---|---|---|
| `sqlparse.parse(sql)` | Lexes + groups tokens into AST | **~1,900 µs/call** |
| `sqlparse.format(sql, ...)` | Parse + reindent/recase | **~2,100 µs/call** |
| `sqlparse.split(sql)` | Split multi-statement SQL | **~600 µs per statement** |
| `sqlparse.tokenize(sql)` | Raw token stream | subset of parse |

The bottleneck is in three places:
1. **[`lexer.py`](file:///home/vscode/.local/lib/python3.12/site-packages/sqlparse/lexer.py)** — regex-match loop in pure Python, character-by-character iteration via `enumerate(text)`
2. **[`engine/grouping.py`](file:///home/vscode/.local/lib/python3.12/site-packages/sqlparse/engine/grouping.py)** — 525 lines of recursive token grouping in Python
3. **[`sql.py`](file:///home/vscode/.local/lib/python3.12/site-packages/sqlparse/sql.py)** — `TokenList` tree with Python object allocation per token

### Key design decisions to make

**1. API compatibility vs correctness tradeoff**

sqlparse is intentionally **non-validating** (it never raises on bad SQL). `sqlparser-rs` is stricter. You need to decide:
- **Drop-in compat**: wrap errors, return best-effort tokens like sqlparse does
- **Strict mode**: expose dialect parameter, raise on invalid SQL

**2. Token type hierarchy**

sqlparse uses a `_TokenType` tuple hierarchy (`Token.Keyword.DML`, `Token.Name`, etc). You'll need to map `sqlparser-rs` AST node types → sqlparse token type strings to maintain compatibility for users doing `tok.ttype == T.Keyword.DML`.

**3. The `Statement` object tree**

The hardest part to replicate is `sql.py`'s `TokenList` tree with methods like `get_alias()`, `get_real_name()`, `token_next_by()`. You can either:
- Return dicts/dataclasses (simpler, breaks compat)
- Implement `#[pyclass]` Rust structs with the same method names (full compat, more work)

**4. Formatter**

`sqlparse.format()` with `reindent=True, keyword_case='upper'` is heavily used. `sqlparser-rs` has a built-in `to_string()` but limited formatting options. You may need to implement the formatter yourself or use [`sql-fmt`](https://github.com/CosmicJaguar/sql-fmt).

---

### Expected speedup

Based on the benchmarks above and what PyO3-based libraries typically achieve:

| Operation | sqlparse (measured) | Expected Rust | Speedup |
|---|---|---|---|
| `parse()` single query | 1,900 µs | ~50–200 µs | **10–40×** |
| `split()` per statement | ~600 µs | ~5–20 µs | **30–100×** |
| `format()` single query | 2,100 µs | ~100–300 µs | **7–20×** |

The lexer is the hottest path — Python's character-by-character `enumerate(text)` with regex match per position is the core bottleneck. Rust's `logos` or `sqlparser-rs`'s own lexer eliminates that entirely.

---

### Recommended first milestone

Start with just `split()` — it's the simplest function, the one with the biggest relative speedup (600 µs → ~10 µs), and the most commonly used in query routing/caching systems. Ship that as `v0.1`, validate compat against sqlparse's test suite, then add `parse()` and `format()`.

## What's next (in priority order)

### Tier 3a — AST grouping (`parse()` returns a real tree)

This is the most complex remaining piece. The Python sqlparse `parse()` runs the flat token stream through a series of **grouping passes** in [`engine/grouping.py`](https://github.com/andialbrecht/sqlparse/blob/0.6.0/sqlparse/engine/grouping.py) that build a tree of [`TokenList`](https://github.com/andialbrecht/sqlparse/blob/0.6.0/sqlparse/sql.py) / `Identifier` / `Function` / `Where` etc. nodes:

- `group_brackets()` — `(...)` → `Parenthesis`
- `group_identifier()` — name+alias → `Identifier`
- `group_functions()` — `name(...)` → `Function`
- `group_where()` — `WHERE ...` → `Where`
- `group_comparison()` — `a = b` → `Comparison`
- `group_alias()` — `x AS y` → `Identifier`
- `group_identifier_list()` — `a, b, c` → `IdentifierList`
- `group_case()`, `group_if()`, etc.

This also requires Rust-backed PyO3 classes for all the AST node types (`Token`, `TokenList`, `Statement`, `Identifier`, `IdentifierList`, `Function`, `Parenthesis`, `Where`, `Comparison`, `Operation`, `Case`) with all their methods (`get_type()`, `flatten()`, `get_alias()`, `get_real_name()`, `get_name()`, `is_group`, `is_whitespace`, etc.).

### Tier 3b — `format()` in Rust

The formatter applies transformations over the AST (after grouping). It depends on Tier 3a being done first. Key options:
- `keyword_case` (upper/lower/capitalize)
- `identifier_case` (upper/lower/capitalize)
- `strip_whitespace`
- `reindent` + `indent_width`
- `strip_comments`
- `output_format` (python/php)

### Tier 3c — Drop-in shim

Once `parse()` and `format()` are Rust-backed, create the `python/sqlparse/` shim package so `import sqlparse` loads our code instead of the real sqlparse. The [`DECISIONS.md`](docs/DECISIONS.md:125) records exactly why this was deferred (circular import trap with `sqlparse._rust`). The current module name `sqlparse_rs` (underscore) was chosen specifically to avoid that conflict until this layer is ready.

## Recommendation

If the goal is **true drop-in replacement**, Tier 3 grouping is the correct next step. But it's a significant undertaking — the Python grouping code is ~600 lines of non-trivial recursive tree-mutation logic, and each node type needs PyO3 bindings.

If the goal is **shipping the Rust speedup** on the hot paths that users actually care about (tokenizing, splitting), the current state is already good — you could publish `sqlparse_rs` as a library crate for Rust users, or expose `tokenize`/`split` in Python as a performance-oriented subset. The 6.8× speedup is real and covers the two operations that dominate in most SQL-parsing workloads.

## What was implemented

### The drop-in lexer patch (`python/sqlparse_rs/`)

**The key insight:** sqlparse's `parse()`, `format()`, and `parsestream()` all funnel through `FilterStack.run()` → `lexer.tokenize()`. By replacing `Lexer.get_tokens` with our Rust implementation, **every** sqlparse operation now uses the fast Rust tokenizer with zero changes to the grouping or formatting engine.

**[`python/sqlparse_rs/_patch.py`](python/sqlparse_rs/_patch.py)** does:
1. Imports `sqlparse_rs.sqlparse_rs.tokenize` (the compiled Rust `.so`)
2. Replaces `sqlparse.lexer.Lexer.get_tokens` with a function that calls Rust and converts `(str, str)` pairs back to `(TokenType, value)` via a cached `sqlparse.tokens.Token` attribute walk
3. Also patches `sqlparse.lexer.tokenize` (the module-level function used by `FilterStack`)
4. Idempotent — safe to call multiple times

**[`python/sqlparse_rs/__init__.py`](python/sqlparse_rs/__init__.py)** fires the patch automatically on `import sqlparse_rs`.

### Current parity table

| API | Status | Notes |
|-----|--------|-------|
| `tokenize()` | ✅ 100% Rust, byte-identical | Differential golden tests |
| `split()` | ✅ 100% Rust, byte-identical | State-machine port |
| `parse()` | ✅ Rust tokenizer + Python grouping | Full AST, all node types |
| `format()` | ✅ Rust tokenizer + Python formatter | All options work |
| `parsestream()` | ✅ Rust tokenizer + Python streaming | File/string input |

### One limitation to communicate to users

`import sqlparse_rs` must come **before** the first `import sqlparse` in the process. In practice: add it to your `conftest.py`, app `__init__.py`, or entry-point module. This is unavoidable because Python caches module objects — once `sqlparse.lexer` is loaded without the patch, you'd need to re-import it.
