---

## Two independent problems

### Problem 1: Committed `.so` artifact poisons `test_independence.py` on other Python versions

`test_independence.py` lines 28–33 detect whether a `.so` exists in the source tree:

```python
_HAS_SRC_SO = any(SRC.glob("sqlparse_rs/sqlparse_rs.*.so"))
```

If any `.so` is found, it sets `PYTHONPATH=python/` so subprocesses import from the source tree. The problem: the **cp312 `.so` is committed to git** (force-added, despite `.gitignore` listing `*.so`). Every CI job on Python 3.9/3.11 checks the repo out, finds the cp312 `.so`, sets `PYTHONPATH=python/`, then spawns subprocesses that try to load a cp312 extension under Python 3.9/3.11 — instant `ModuleNotFoundError`.

**Long-term fix: two-part**
1. **Remove the `.so` from git tracking** — it is a build artifact, `.gitignore` already says so, and it has no business in the repository.
2. **Harden the detection logic** in `test_independence.py` to check that the found `.so` is ABI-compatible with the running Python, rather than just testing existence:
   ```python
   import sysconfig
   _ext_suffix = sysconfig.get_config_var("EXT_SUFFIX")  # e.g. .cpython-312-x86_64-linux-gnu.so
   _HAS_SRC_SO = (SRC / "sqlparse_rs" / f"sqlparse_rs{_ext_suffix}").exists()
   ```
   This way a cp312 `.so` on disk is invisible to a Python 3.11 runner: `_HAS_SRC_SO` goes `False`, PYTHONPATH is cleared, and the test uses the installed wheel from site-packages — which is the cp311 wheel the CI job just built and installed.

---

### Problem 2: Duplicate `pyproject.toml` with a fragile relative path

There are two `pyproject.toml` files:

| File | `python-source` |
|---|---|
| [`pyproject.toml`](pyproject.toml) (root) | `"python"` — correct, always relative to repo root |
| [`crates/sqlparse-py/pyproject.toml`](crates/sqlparse-py/pyproject.toml) | `"../../python"` — relative to the file's directory, so also resolves correctly **when maturin reads that file** |

The current CI was accidentally using `--manifest-path crates/sqlparse-py/Cargo.toml`, which caused maturin to read the crate-level `pyproject.toml`. Maturin resolves `python-source` relative to the **pyproject.toml's own directory** (confirmed by the subagent), so `../../python` was actually correct in isolation — but the actual bug was that maturin was silently ignoring that setting in some cases and only including the `.so`.

The deeper design issue: **having two `pyproject.toml` files that need to stay in sync is a maintenance hazard**. The canonical maturin mixed-layout has exactly one `pyproject.toml` at the repo root with both `manifest-path` (pointing into `crates/`) and `python-source` (pointing at `python/`). The crate-level `pyproject.toml` is redundant and will drift. 

**Long-term fix:** Delete [`crates/sqlparse-py/pyproject.toml`](crates/sqlparse-py/pyproject.toml) entirely. The root `pyproject.toml` is the single source of truth, and `maturin develop`/`maturin build` are always invoked from the repo root (this is already documented in `AGENTS.md`). The only reason to keep the nested file would be to support `cd crates/sqlparse-py && maturin build`, which is explicitly discouraged.

---

### Summary

| Issue | Root cause | Long-term fix |
|---|---|---|
| Tests fail on Python 3.9/3.11 | cp312 `.so` committed to git; `_HAS_SRC_SO` is version-blind | Remove `.so` from git; use `sysconfig.get_config_var("EXT_SUFFIX")` for exact-match detection |
| Wheel missing Python files | CI used `--manifest-path` which selected the wrong pyproject.toml | Already fixed; long-term: delete `crates/sqlparse-py/pyproject.toml` to eliminate drift risk |

## What's actually blocking lower Python versions

### Nothing fundamental — pyo3 0.23 supports Python 3.7+

---

### The right long-term approach: `abi3`

Right now every Python version requires a separate build + wheel. The better approach is pyo3's **`abi3` feature**, which compiles against the stable CPython ABI and produces a single wheel that runs on any Python ≥ the chosen minimum:

```toml
# crates/sqlparse-py/Cargo.toml
pyo3 = { version = "0.23", features = ["extension-module", "abi3-py38"] }
```

This produces a wheel tagged `cp38-abi3-linux_x86_64` (or `none-abi3`) instead of `cp312-cp312-…`. That single wheel installs and runs on Python 3.8, 3.9, 3.10, 3.11, 3.12, 3.13 — no per-version builds needed.

**Tradeoffs:**
- Slightly slower at runtime (abi3 disables a few internal CPython shortcuts)
- Some newer pyo3 APIs are not available (anything not in the stable ABI spec). Everything currently used — `PyString`, `PyTuple`, `PyList`, `PyDict`, `PyModule`, `pyfunction`, `pymodule` — is all stable ABI
- maturin handles the wheel tag automatically when it sees `abi3` in the features

**CI with abi3:** one build, one wheel, all versions test against it — the matrix can go back to `["3.9", "3.11", "3.12"]` with a single shared artifact. `test_independence.py` works correctly because all Python versions load the same `abi3` `.so` via the installed wheel (no source-tree `.so` present).
