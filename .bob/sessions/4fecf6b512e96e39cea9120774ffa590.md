## 🤖 Assistant

The two imports are **not both needed** — `import sqlparse_rs` is enough. The second `import sqlparse` is only needed because you want to *use* `sqlparse`'s API. The comment in the README is misleading. Here's the real picture:

---

### What actually happens with one import

```python
import sqlparse_rs   # ← this is the only "special" line
```

When this executes, `__init__.py` runs [`_install_patch()`](python/sqlparse_rs/_patch.py:8), which internally does `import sqlparse` itself and monkey-patches three things on it:

| What gets patched | With |
|---|---|
| `sqlparse.lexer.Lexer.get_tokens` | Rust scanner |
| `sqlparse.lexer.tokenize` | Rust scanner |
| `sqlparse.parse` | Rust tokenize + grouping |
| `sqlparse.format` | Rust formatter |

After that, any subsequent `import sqlparse` in *any* module gets the already-patched version from Python's module cache — no second `import sqlparse_rs` is ever needed.

### So why does the example show two imports?

```python
import sqlparse_rs   # ← fires the patch
import sqlparse      # ← just to get a name to call sqlparse.parse(...) with
```

The second line is **not about patching** — it's simply bringing `sqlparse` into the local namespace so you can call `sqlparse.parse(...)`. If you don't need to use `sqlparse` directly, you don't need it at all. You could equally write:

```python
import sqlparse_rs
sqlparse_rs.parse("SELECT 1")   # Rust directly
```

Or, if you prefer the `sqlparse` API:

```python
import sqlparse_rs   # patches sqlparse in one shot
import sqlparse      # just a name alias — already patched

sqlparse.parse("SELECT 1")      # runs Rust under the hood
```

### The one real constraint

`import sqlparse_rs` must happen **before the first call to any `sqlparse` function** (not necessarily before `import sqlparse` itself, since the patch fires on `sqlparse_rs` import, not deferred). The only edge case where order matters is if something else calls `sqlparse.parse()` at module import time before your `import sqlparse_rs` has run — which is uncommon. The safest convention is to put it first.

### What would it take to make sqlparse optional?

The goal of the project is a **drop-in replacement** for sqlparse. That means the `Statement`, `Where`, `Identifier` Python objects — the entire AST API — are inherited from `sqlparse`. Removing that dependency would mean reimplementing those ~20 Python classes from scratch in Python (or as PyO3 types), which is a significant separate project.

The only part that's fully independent of sqlparse today is:
- `sqlparse_rs.tokenize()` — pure Rust, no sqlparse needed
- `sqlparse_rs.split()` — pure Rust, no sqlparse needed

Everything else (`parse`, `format`, `parsestream`, all sub-modules) requires sqlparse at runtime. That's not a gap to close — it's the architecture. `sqlparse_rs` accelerates sqlparse; it doesn't replace it entirely at the Python layer.
